# Правила работы над проектом

Этот файл читает Claude Code каждый раз, когда открывает проект.
Он задаёт правила, по которым помощник пишет код. Здесь же лежат мои
собственные правила обучения — их менять по ходу можно и нужно.

## О проекте

«Радар вакансий» — учебный, но рабочий проект: каждое утро собирает вакансии
из открытых источников, приводит их к единому виду, считает статистику по рынку
и в 12:00 присылает в Telegram подборку под мой профиль.

Автор учится по ходу дела. Цель проекта — не «быстро получить результат»,
а понять каждый инструмент настолько, чтобы объяснить его на собеседовании.

## Главное правило

**Объясняй, а не просто делай.** К любому куску кода — короткое объяснение
на русском: что он делает, зачем нужен и какие были альтернативы.
Если я прошу «сделай X», а из вопроса видно, что я не понимаю, как X устроен —
сначала объясни устройство, потом код.

Не пиши сразу большой файл. Максимум один смысловой кусок за раз,
чтобы я успевала разобрать его построчно.

## Технические правила

- Язык: Python 3.11+, SQL (диалект BigQuery Standard SQL).
- Комментарии и docstring — на русском, названия переменных и таблиц — на английском.
- Никаких секретов в коде. Ключи и токены — только через переменные окружения
  (`os.environ`) и GitHub Actions secrets. В репозиторий не попадает `.env`.
- Каждая новая dbt-модель приходит вместе с тестами в yml-файле.
  Минимум: `unique` и `not_null` на ключ.
- В моделях слоя marts не использовать `select *` — перечислять колонки явно.
- Сырой слой (`raw`) не изменяем и не чистим: он хранит то, что пришло из источника,
  как есть. Вся обработка — в dbt.
- Ошибки не глотать: если запрос к источнику упал, скрипт должен упасть с понятным
  сообщением, а не записать пустоту.
- Зависимости добавлять в `requirements.txt` с указанием версии.

## Слои данных

| Слой | Что там лежит | Где живёт |
|---|---|---|
| `raw` | сырые ответы источников, как пришли | data/*.jsonl, потом BigQuery |
| `staging` | те же данные, но причёсанные: типы, регистр, дубли | dbt models/staging |
| `marts` | витрины для дашборда и бота | dbt models/marts |

## Порядок работы

1. Обсуждаем, зачем нужен шаг, и какую проблему он решает.
2. Я пишу первую версию сама (или разбираю предложенную построчно).
3. Прогоняем, смотрим на результат глазами.
4. Записываю вывод своими словами в `decisions.md`.
5. Коммитим маленьким коммитом с осмысленным сообщением.

## Чего делать не надо

- Не добавлять инструменты, которых нет в плане (Kafka, Kubernetes, Spark, Airbyte).
- Не усложнять ради красоты: лишний слой абстракции хуже, чем понятный прямой код.
- Не писать код, который я не смогу объяснить вслух. Если получилось сложно —
  упростить или объяснить подробнее.


Любой шаг, который обрабатывает список, продолжает работу после сбоя на одном элементе: сбой логируется, остальные обрабатываются. Падать целиком — только если не удалось обработать ни одного. Результаты сохраняются частями, а не в конце.
